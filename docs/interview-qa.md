# 面试问答要点

## 1. 为什么用 Redis + Lua 做库存预扣，而不是直接扣数据库？

- **性能**：库存扣减是下单链路最高频操作，直接 `UPDATE stock SET available = available - ? WHERE sku_id = ? AND available >= ?` 在高并发下会产生大量行锁竞争。Redis 是单线程命令执行，`get` + `decrby` 写成一段 Lua 脚本原子执行，RT 可到毫秒级。
- **正确性兜底**：Redis 是缓存，可能存在与 DB 不一致或宕机丢数据。所以：
  - Lua 保证「读可用量 + 校验 + 扣减」三步原子，避免并发超卖；
  - 扣减后落 `stock_deduct_log`，用唯一索引 `(order_id, sku_id, type)` 兜底幂等，重复请求命中唯一键冲突直接返回成功；
  - DB 侧再用条件更新 `WHERE available >= qty` 双保险。
- 一句话：**Redis 求快，DB 求准**，两层都在防超卖。

## 2. 如果 Redis 和数据库不一致了怎么办？

- 正常路径：预扣成功 → 落流水 + DB 条件更新；确认/回补也同步改 DB 和 Redis。
- 异常路径：如果「Redis 扣了但 DB 没扣」，靠 `stock_deduct_log` 唯一索引在重试时幂等补齐；如果消息/调用失败，靠「下单失败即回补」和「延迟队列超时取消回补」补偿。
- 服务启动时 `ApplicationRunner` 会用 DB 的 `available` 重建 Redis 缓存，作为最终对账兜底。

## 3. 订单状态机怎么实现的？为什么不用 Spring StateMachine？

- 用 `EnumMap<状态, Map<事件, 目标状态>>` 做转移表，`transition(当前状态, 事件)` 查表返回目标状态，非法转移抛业务异常。
- 状态落库用 CAS 条件更新 `WHERE status = 当前状态`，防止并发重复流转（比如支付和取消同时到达）。
- 不用 Spring StateMachine：本项目状态少（6 个）、转移明确，手写几十行就能讲清楚，引入框架反而增加学习和调试成本；面试时重点表达「按场景选型，不为用而用」。

## 4. 延迟队列实现超时取消，和定时任务扫描订单表比有什么优劣？

- 延迟队列（RabbitMQ TTL + 死信）：只处理到期的消息，不扫全表，扩展性好，解耦；代价是引入 MQ 的复杂度，消息可能丢失需要补偿。
- 定时扫描：实现简单、直观，但订单量大时是全表扫描 + 大量空轮询，且扫描周期是精度与开销的折中。
- 本项目选延迟队列，同时保留「消费时校验订单仍为待支付」的幂等，以及定时补偿兜底最终一致。

## 5. ThreadPoolExecutor 的参数怎么定的？为什么拒绝策略选 CallerRunsPolicy？

- 核心 8 / 最大 16 / 有界队列 200：分拣是 IO 密集（查库、打标），线程数按 CPU 核数 ×2~4 估算；有界队列防止任务无限堆积打爆内存。
- `CallerRunsPolicy`：队列打满时由调用线程同步执行，宁可让上游变慢也不丢弃任务——分拣任务丢弃会导致订单卡在分拣中，业务上不可接受。
- 主线程用 `CountDownLatch` 等待全部子任务完成再汇总，比逐个 `join` 更简洁、可读。

## 6. 为什么用 Elasticsearch 做异常检索，而不是 MySQL 模糊查询？

- 履约异常需要按「团长 / 商品 / 时间区间」多条件组合检索，且字段多、数据量随订单增长。MySQL `LIKE '%x%'` 无法走索引、组合条件效率低，数据量大后退化为秒级。
- ES 的倒排索引 + `bool/term/range` 组合查询天然适合这种多维过滤，毫秒级返回。
- 一致性策略：MySQL 为准，落库后同步 ES，写 ES 失败仅告警，查询时 ES 不可用自动降级 DB——保证「检索可降级、数据不丢」。

## 7. 如何保证最终一致性？

- **本地事务**：订单 + 明细在同一 MySQL 事务内落库。
- **消息**：支付成功/取消等状态变更后发 RabbitMQ 消息异步通知下游（履约/库存）。
- **补偿**：超时取消走延迟队列；履约异常走 `@Scheduled` 定时补偿；消息发送失败同步回补。
- **幂等**：消费端都做状态校验（如「仍为待支付才取消」），重复消费不会重复流转。

## 8. 接口幂等怎么做的？

- 库存预扣：`stock_deduct_log` 唯一索引 `(order_id, sku_id, type)`，重复请求 INSERT 冲突即幂等返回。
- 订单状态流转：CAS 条件更新 + 状态机校验，重复事件第二次更新影响行数为 0。
- 分拣回调：`startSort/sortDone` 内部判断当前状态，已处理则跳过。

## 9. 为什么选择 Spring Cloud Alibaba / Nacos？

- Nacos 同时提供注册中心 + 配置中心，一套组件满足两者，运维成本低，社区活跃、国内资料多。
- 本项目演示用 Nacos 注册发现 + 本地 yml 配置；OpenFeign + LoadBalancer 做服务间调用与负载均衡。

## 10. 这个项目如果上生产，还差什么？

- 真实支付网关（支付宝/微信）、分布式事务（Seata）或本地消息表的更严谨实现、Redis 集群 + 哨兵、ES 集群、限流熔断（Sentinel）、全链路日志与监控（SkyWalking/Prometheus）、CI/CD、密钥托管（Nacos 配置中心 / 环境变量注入）。
